## Semántica que conviene conocer

- La interfaz empieza siempre en modo demostración. Para operar hay que iniciar sesión.
- El dashboard muestra **inventario provisionado**, no consumo agregado real de CPU/RAM.
- Un 501 significa que el conector no implementa esa capacidad; no simula éxito.
- Proxmox devuelve contadores de red; no son tasas por segundo. En Kubernetes los campos de red son 0 como valor no disponible del contrato v0.1; no deben interpretarse como ausencia de tráfico.
- Los campos no proporcionados por XAPI/vCenter, como capacidad agregada de host, pueden ser 0 o cadena vacía. Trátalos como “no disponible”.
- La API de acciones de VM es síncrona. Tras un timeout consulta el proveedor antes de reintentar: la operación remota podría continuar.
- La importación usa merge de registros ausentes. La auditoría incluida en una exportación es para consulta, no se reescribe en destino.
- Una exportación `infrastructure` de un job guarda configuración de infraestructuras; `targets` se utiliza en jobs de VM, no filtra exportaciones de configuración en esta versión.
- La integración de webhooks tiene semántica al menos una vez; no garantiza exactamente una vez.
- Los plugins forman parte de la base de confianza del servidor. El proceso hijo no es una frontera de seguridad para código malicioso.

## Antes de un despliegue enterprise

La siguiente fase debe validar contratos en versiones reales de Proxmox, Kubernetes, XAPI y vCenter; completar las funciones marcadas pendientes que sean necesarias para el entorno; probar recuperación de PostgreSQL/Redis y la clave maestra; añadir una outbox de eventos y operaciones durables; y revisar límites, escalado, auditoría externa y aislamiento de plugins. No se atribuyen aquí certificaciones, resultados de benchmark ni compatibilidad no observada.
